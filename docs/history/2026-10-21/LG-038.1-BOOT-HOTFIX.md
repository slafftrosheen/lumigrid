# LG-038.1 boot hotfix

Baseline: main 0f1198dd4944299101ddc5a8b1dcf1838f9ec54a.

Current status: consolidated image flashed and all four hashes verified on COM4.
Physical idle boot passes: app_main, all required startup services and Ready
heartbeats observed through 73.5 seconds, with no panic/reset in the captures.
Main task minimum free stack is 7148/10240 bytes. Idle free heap is only about

Current evidence: LG-038.1-boot-log.txt. Earlier captures below refer to previous

## Framework constraint

PlatformIO espressif32@6.7.0 supplies ESP-IDF 5.2.1. Its hidden
FREERTOS_SUPPORT_STATIC_ALLOCATION option is always enabled, and
FreeRTOSConfig.h hardcodes configSUPPORT_STATIC_ALLOCATION=1 and
configUSE_TIMERS=1. Config regeneration restores static allocation to y.
The requested sdkconfig-only disable therefore cannot change scheduler behavior.
No framework patches or custom application idle/timer memory hooks are introduced.

Approved owner exception: scripts/boot_memory_policy.json declares ESP-IDF
port_common.c as scheduler-memory owner for this exact platform/framework pin.
The invariant allows generated factory static allocation only with that owner
and its documentation. Project defaults still reject enabling it. Platform
changes require revisiting this exception. CI checks again after factory config
regeneration; application idle/timer hooks are forbidden.

Sources: https://github.com/espressif/esp-idf/blob/v5.2.1/components/freertos/Kconfig
and https://github.com/espressif/esp-idf/blob/v5.2.1/components/freertos/config/include/freertos/FreeRTOSConfig.h.

## Pre-scheduler DRAM

The first clean telemetry build reserves 130480 bytes for app_main's static
LumigridRuntime object, before scheduler startup. Two inline LiveDmxFrame buffers
are moved to checked, separately owned heap allocations in the LightingRuntime
constructor, called after app_main begins. Capacity and runtime lifetime are
preserved. Lighting startup rejects missing buffers with ESP_ERR_NO_MEM.
This reduces pre-scheduler static DRAM; it does not reduce total runtime frame
storage. The physical boot log is required to establish causality and acceptance.

## Telemetry and acceptance

BOOT_HEAP precedes runtime construction and reports free/largest 8-bit memory,
free/largest internal memory, free heap and minimum heap. Startup stages include
ConfigStore, OutputController, PCA9685, addressable topology, LightingRuntime,
Wi-Fi, HTTP API, mDNS and certification. RMT_ALLOC records A port, GPIO, RGB/RGBW,
pixel count, wire bytes, result and internal heap after configuration. No per-frame
heap logging is added.

Capture power-on through at least ten seconds: require main_task, app_main,
BOOT_HEAP and runtime startup, without timer-task assertion or reset loop.
Start with A and P ports disabled; then P1; then A1 with 30 pixels; only then
increase topology. Eight-channel allocation and output certification remain
physical acceptance gates, not claims inferred from compilation.

## Separate storage defect

from the timer-task allocation assertion. Preserve this partition table for the
hotfix. A later storage batch must align board size, defaults, partition table,
OTA slots and filesystem together for the intended production module.

## First physical boot capture

The recovery flash reached main_task and app_main with BOOT_HEAP free8=160092,
largest8=110592, internal=199316, largestInternal=110592, freeHeap=160092,
minimum=160092. The timer-task assertion no longer occurs. A later heap-walk
LoadProhibited panic after PCA9685 initialization still reset the board.
The symbolized trace ends in log_heap_stage, heap_caps_get_largest_free_block,
multi_heap_get_info_impl and tlsf_walk_pool.

PCA9685 configured trans_queue_depth=4. In the pinned IDF i2c_master.c this
enables asynchronous transfers even without a registered callback. The driver
uses stack-local readback bytes and immediately validates them; async completion
violates their lifetime. Set trans_queue_depth=0 to preserve synchronous
completion while the mutex is held. The invariant rejects returning to async
mode with stack buffers. Subsequent physical capture is required for acceptance.

Raw capture: docs/lg0381-boot-manual.log (local ignored artifact).

## Second physical boot capture

Synchronous I2C removes the heap-walk panic; startup reaches ConfigStore and
LightingRuntime. PCA9685 truth is ESP_ERR_NOT_FOUND at 0x55 and 0x40. PWM testing
is blocked until the peripheral is present, while idle startup may continue.
The next blocker is a main-task stack overflow in certification initialization.
CertificationStore placed multiple approximately 6.7 KB record values on the
10 KB main stack, including two slot records in load(). Move startup/load/save
scratch records to checked heap ownership and reset owned records in place
without large aggregate stack temporaries. Do not enlarge the scheduler's main
stack to mask this issue. Raw capture: docs/lg0381-boot-final-power.log.

Compiled regression evidence: the previous image is rejected by
verify_boot_stack.py because CertificationStore::save uses a 6736-byte stack
frame. The corrected image passes: init=64, load=80 and save=64 bytes. Factory
post-link checks enforce a 1024-byte scratch-frame budget for these functions.
This checks generated code, not only a source pattern. Full startup stack usage
and final idle stability still require target observation.

## Network startup stack and handler capacity

The next capture passes certification and starts Wi-Fi, then reports
ESP_ERR_HTTPD_HANDLERS_FULL and a main-task stack overflow. FactoryApi::start
had a 3680-byte frame nested under runtime start (3216) and network-service
startup (1872), before deeper library/logging calls. Move immutable HTTP route
tables into flash, bind user_ctx on a single temporary registration descriptor,
and derive max_uri_handlers from both route table lengths instead of hardcoded
80. The post-link guard bounds FactoryApi::start to 2048 bytes. BOOT_STACK logs
the main task's observed minimum remaining stack after startup. Main stack
configuration remains 10240 bytes. Capture: docs/lg0381-boot-stack.log.

API startup now emits a 1648-byte frame (previous 3680), passes the 2048-byte
compiled guard, and computes handler capacity from the route arrays. The final
source build uses 142516 static RAM bytes and 1295017 flash bytes. Configuration
and linked stack guards passed. Device validation of this image is pending.

## Combined startup stack correction

The HTTP-table fix alone still overflows main at api.start; raw capture is
docs/lg0381-boot-api.log. Its individual frame passed, but the combined runtime
start/network/API chain retained too much stack. Move DeviceConfig snapshots in
both parent startup methods to checked heap ownership and reuse the first
snapshot after Wi-Fi startup. Emitted frames are now runtime_start=592 and
network_start=560 bytes, down from 3216 and 1872. The post-link guard now
requires both parent frames below 1024 bytes as well as the API frame below
2048. Main stack remains 10240 bytes. Eight config regression tests and
git diff --check pass; factory build passes with flash usage 1294965 bytes.
Target idle acceptance remains pending for this correction.

## Upstream research and complete-path audit (2026-10-05)

Read the pinned ESP-IDF 5.2.1 upstream source, not a generic vanilla-FreeRTOS
recipe. port_common.c allocates idle/timer TCBs and stacks through pvPortMalloc
and asserts on allocation failure. heap_idf.c requests internal, 8-bit-capable
memory. Static-allocation support does not mean the port supplies compile-time
static buffers. Reducing application .bss is the appropriate remedy for this
pre-scheduler shortage; disabling the hidden Kconfig option cannot remedy it.

Sources:
- https://github.com/espressif/esp-idf/blob/v5.2.1/components/freertos/port_common.c
- https://github.com/espressif/esp-idf/blob/v5.2.1/components/freertos/heap_idf.c
- https://github.com/espressif/esp-idf/blob/v5.2.1/components/esp_http_server/src/httpd_main.c
- https://docs.espressif.com/projects/esp-idf/en/v5.2/esp32/api-guides/performance/ram-usage.html

httpd_start creates a separate HTTP worker using config.stack_size. The observed
crashing task is main, so changing the HTTP worker's stack does not address this
startup overflow. Espressif recommends removing large automatic variables and
checking task stack high-water marks. No matching upstream fix for this specific
application startup overflow was established by the GitHub searches.

The latest ELF direct-call audit finds retained large configuration records in
ConfigStore::load_config, its migration lambda, scene initialization and API
identity startup. The conservative app_main path estimate is 9776 bytes against
a 10240-byte main stack; it includes exception-unwind paths and excludes indirect
calls, ROM frames and interrupts. It is evidence to guide a full configuration
scratch-storage review, not a certified worst-case bound. Individual frame guards
cannot establish whole-call-chain safety. Do not treat the unflashed parent-frame
correction as proof of stable idle. Further startup work must consolidate large
configuration/migration scratch ownership and review the full chain before any
additional target validation.

## Consolidated boot hardening

Current candidate: .pio/build-lg0381-solid/factory, from a new clean build
followed by source verification. Final flash usage 1295369/1310720 bytes; static
RAM 142516 bytes. The four-image size/SHA256 manifest is lg0381-images.json in
that build directory. No partition, header size, main stack size or framework
changes. No target flash is performed before this candidate passes the offline
gates and the board is placed in the downloader.

- Device/configuration backup, verification and legacy migration scratch records
  use invocation-local checked heap ownership; normal scene loads allocate no
  legacy topology snapshot. Scratch is not shared across tasks.
- Scene initialization loads into its owned scene buffer; blackout fallback
  reconstructs it in place with the original default values.
- Config/scene default writes and allocation failures propagate; defaults are not
  written on unrelated NVS errors. Config save acquires verification scratch
  before touching NVS, preserving backup-write ordering.
- Runtime init, API identity initialization and certification initialization use
  checked configuration scratch. It is released before deeper startup work.
- Recovery/network-apply task creation, network readiness semaphore, lighting
  shutdown semaphore, authentication and certification initialization are checked.
  app_main logs BOOT_FAILED and does not call start after a failed init. Required
  API/mDNS/fleet/Art-Net/sACN startup errors propagate and prevent Ready; startup
  rollback blacks out and disables outputs while retaining available recovery
  Wi-Fi/API access.

Linked frames: app_main=80, runtime_init=320, runtime_start=592,
network_start=560, api_start=304, scene_init=64, config_load=64,
scene_load(max including lambdas)=192, scene_save=80,
cert_service_init=64, cert_store_init=64, cert_store_load=80,
cert_store_save=64 bytes. The linked guard covers all these and rejects an
acyclic direct-call startup path exceeding 7680 bytes (75% of the unchanged
10240-byte main stack). Current direct-call estimate: 5072 bytes. This excludes
indirect calls, recursion depth, ROM and interrupt frames; it does not replace
target stack high-water telemetry.

Offline verification: eight boot policy regression tests, seven linked-stack
guard tests, invariant checks, existing runtime math/protocol simulations,
clean factory build and final source rebuild, and git diff --check pass. These
are not target proof of OOM handling, legacy migration, or output certification.
Device acceptance requires one consolidated flash, power-on log, all required
startup stages, BOOT_STACK headroom and sustained Ready heartbeats without reset.
PCA9685 remained absent at 0x55/0x40 in previous target captures; PWM acceptance
requires that hardware. All A/P ports remain disabled for the idle boot gate.

Memory limit: startup-stage telemetry uses MALLOC_CAP_INTERNAL, which can include
IRAM unavailable to ordinary 8-bit data allocations. Its roughly 39 KB largest
block must not be treated as ordinary heap capacity. Heartbeat esp_get_free_heap_size
shows the actual approximately 4.7 KB idle 8-bit headroom. Protocol workers retain
4 KB stacks each; main retains its 10 KB stack for heartbeat logging. These are
runtime headroom candidates for a later consolidated memory pass, not stacks to
blindly shrink. No loaded topology, eight-channel RMT allocation, HTTP interaction,
fresh-NVS boot or injected allocation-failure acceptance has been established.
Do not infer those from this idle boot result.
